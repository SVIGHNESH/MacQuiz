2. Auth & JWT revocation

backend/app/api/v1/auth.py issues JWTs on /login / /login-json. Revocation is handled by two small tables rather than a stateful session store:

  • revoked_tokens — stores a token's jti until it would have expired naturally (single-token logout, /logout).
  • user_token_blocks — one row per user holding revoked_before; any token with an earlier iat is rejected globally (/logout-all, password change). This is O(1) regardless of how many tokens a user has issued, instead of enumerating and blacklisting every outstanding token.

3. Hosting model — the biggest lever

Vercel Python functions are stateless: no warm process, no warm connection pool. Bursty traffic (a class opening a live quiz at the same second, hammering POST /attempts/start) spins up many cold containers, each paying cold-start and a fresh Postgres handshake. The fix applied here is architectural, not a code tweak: run the backend as a single always-warm process.

Resolution done — Render free web service

render.yaml (repo root) defines a runtime: python web service on Render's free plan, started with uvicorn app.main:app --host 0.0.0.0 --port $PORT — a long-lived process, not a per-request function. Frontend stays on Vercel as a static build. See Deployment for the full setup and required env vars.

4. Database connection strategy

backend/app/db/database.py branches connection behavior by host, not by a single hardcoded assumption:

if os.getenv('VERCEL') or os.getenv('SERVERLESS'):
    engine_kwargs["poolclass"] = NullPool   # no pooling across stateless invocations

Independently of that, any Postgres URL gets connect_args = {"prepare_threshold": None} (not gated behind the Vercel check) because it fixes a different problem: Supabase's :6543 endpoint is the PgBouncer transaction pooler, which does not support server-side prepared statements. psycopg3 issues them by default, causing "prepared statement already exists" errors under concurrency — exactly the concurrent-quiz scenario this app needs to survive. On Render (no VERCEL/SERVERLESS env var set), the engine keeps SQLAlchemy's default pooled QueuePool, giving a real warm connection pool for free.

5. Startup / bootstrap

The FastAPI lifespan in main.py is now a no-op. Schema creation and admin-user seeding live in backend/app/bootstrap.py, run once per deploy via python -m app.bootstrap (idempotent — safe to re-run). /health does a live SELECT 1 probe on each call instead of reporting a boot-time flag, so it reflects current DB reachability without the app touching the DB during cold start.

6. Frontend delivery

frontend/src/App.jsx lazy-loads the admin-only routes with React.lazy() + Suspense (AdminDashboard, QuizCreator, QuizTaker, QuizResult); only Login is statically imported since every visitor needs it. vite.config.js splits react/react-dom/react-router-dom and lucide-react into separate cacheable vendor chunks via build.rollupOptions.output.manualChunks. A student opening the login page no longer downloads the multi-thousand-line admin dashboard bundle.

7. Analytics query shape

backend/app/api/v1/analytics.py's get_dashboard_stats uses func.count(col).filter(...) aggregate columns (SQL FILTER (WHERE ...)) to compute paired total/active metrics in a handful of round trips instead of one sequential .count() per metric, wrapped in a 45s in-process TTL cache. get_recent_activity is a single 3-table join (QuizAttempt + User + Quiz) instead of one query per attempt in a loop.

8. List endpoint pagination & filtering

get_all_users and get_all_quizzes accept role/department/search query params and validated skip/limit bounds, so large orgs don't get an entire table shipped to the browser for client-side filtering. See Fix Status for exactly which frontend views were wired to pass these down versus left as future work.
